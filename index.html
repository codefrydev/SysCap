Why Servers Run Out of RAM (OOM)

Reading from RAM takes ~100 ns, while reading from NVMe SSD takes ~100,000 ns (1,000× slower). Keep at least 20% of your active DB indexes in RAM plus 25% free OS page cache to prevent swap thrashing during traffic spikes.

Systems Engineering Field Guide

How Server Capacity Planning Actually Works

Whether you are deploying your first VPS or designing a distributed cluster, server sizing boils down to four fundamental laws: Little's Law for Concurrency, CPU Time Slicing, RAM Working-Set Caching, and I/O Bandwidth.

LAW 01 // CONCURRENCY

Little's Law: Why Slow Queries Kill Servers

L = λ × W

The number of active concurrent connections (L) equals your arrival rate (λ = Requests/sec) multiplied by the average time a request takes (W = Latency in seconds).

// Example Comparison at 500 RPS:
Fast API (20ms response): 500 × 0.02s = 10 concurrent reqs
Slow DB Query (800ms response): 500 × 0.80s = 400 concurrent reqs!

Takeaway: Optimizing a slow database query from 800ms down to 20ms reduces the number of simultaneous connections holding onto server RAM and worker threads by 40×!

LAW 02 // COMPUTE

The 1,000 Millisecond CPU Budget

1 Core = 1,000ms/s

Every 1 vCPU core gives you exactly 1,000 milliseconds of CPU compute time per second. Note that waiting on a database or external API over the network (I/O wait) does not burn CPU ms if your server uses async I/O.

// How many RPS can 1 vCPU core handle?
Static / Cached JSON (2ms CPU): 1000 ÷ 2ms = 500 RPS / core
SSR React / Heavy ORM (25ms CPU): 1000 ÷ 25ms = 40 RPS / core
Bcrypt Password Hash (100ms CPU): 1000 ÷ 100ms = 10 RPS / core

Takeaway: Always provision enough cores so peak traffic stays under 70% CPU utilization. Above 80%, queuing theory causes latency to spike nonlinearly.

LAW 03 // MEMORY HIERARCHY

How Much RAM Does a Database Actually Need?

20% Working Set

You do not need enough RAM to fit your entire 500 GB database in memory. You only need enough RAM to hold your B-Tree Indexes and "Hot Working Set" (typically 15%–25% of total DB size).

// Where Server RAM Goes on a 16 GB Node:
Linux Kernel + Systemd + Agents: ~0.8 GB
App Workers (e.g., 8 × 150MB): ~1.2 GB
DB Buffer Pool (40%–60% of RAM): ~8.0 GB
OS File Cache & Safety Headroom: ~6.0 GB

Takeaway: If your database has to hit disk for every index lookup, your server's RPS capacity drops by 10×–50× while waiting on disk IOPS.

LAW 04 // NETWORK & DISK

Bytes vs. Bits (Why 100 Mbps ≠ 100 MB/s)

1 Byte = 8 Bits

Network cards are measured in Megabits per second (Mbps), while your files and JSON payloads are measured in Kilobytes / Megabytes (KB / MB). Always multiply payload Megabytes by 8 (or ~9 with TCP/TLS overhead) to get Megabits!

// Network Conversion Cheat Sheet:
100 Mbps Port Max Transfer: ~11.5 MB / sec
1 Gbps (1000 Mbps) Port Max: ~115 MB / sec
1 TB Monthly Bandwidth Limit: ~3.1 Mbps continuous 24/7

Takeaway: Serving 1 MB images directly from your app server at 200 RPS requires 1,600 Mbps (1.6 Gbps)—saturating a standard 1 Gbps NIC immediately. Offload images/videos to a CDN!
